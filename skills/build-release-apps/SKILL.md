# 应用开发与发布工作流

## 目标

把每一项应用修改交付为：架构合理、无废弃代码、模块职责清晰、带版本号且可发布的成果；新应用和文档、Skill 还需经过验证。

## 适用范围与优先级

- 适用于新应用、现有应用、网站、桌面程序、CLI、移动应用及其后端。
- 纯文档和不产生代码变更的 Skill：验证通过后直接提交并发布版本，不请求确认；不需要打包的任务不生成产物。
- 已有应用的代码修改：不运行格式、类型、测试、浏览器或产物验证，不请求发布确认；完成修改并生成带版本号的发布产物后，直接提交、推送并发布 GitHub Release。生成产物所必需的构建可以执行，但不作为验证。发布说明必须注明“未验证：按用户要求跳过验证”，不得声称验证通过。
- 新应用的代码修改：完成适用验证和带版本号的产物后，请求一次明确发布确认。
- 遵守项目现有约定；本 Skill 与用户当前明确要求冲突时，以用户当前要求为准。
- 不执行破坏性操作；共享状态操作仍需遵守权限与安全边界，跳过验证不等于跳过密钥检查、凭据保护或发布前置条件检查。

## 将用户内容转换为 AI 易理解的形式

每次实现用户需求或创建、更新 Skill 时，先把用户的口头表达整理为明确指令，不直接复制原文。

1. 提取目标：用户最终希望得到什么。
2. 明确触发与范围：何时执行、适用于哪些项目、哪些内容不在范围内。
3. 列出输入与约束：已有资料、环境条件、必须遵守或禁止的行为。
4. 拆分执行步骤：按依赖顺序写成可执行动作，每步只承担一个主要职责。
5. 定义输出与验收：产物格式、质量要求、验证方式和完成条件。
6. 补充例外与异常处理：仅补充合理且必要的边界，不虚构需求。
7. 用简短示例消除歧义；无法合理推断的关键信息，先问最少的问题。

要求：

- 保留用户原意，明确区分“用户明确要求”与“为实现目标采用的合理默认值”。
- 使用命令式句式、明确条件、有序步骤和可验证结果，避免“做好一点”“优化一下”等模糊表述。
- 不为 Skill 添加与目标无关的说明文件、功能或抽象。
- 写入 Skill 时，将触发条件放入 frontmatter 的 `description`，将执行规则放入正文。
- 完成后自检：AI 能否据此判断何时触发、做什么、不能做什么、怎样算完成。

## 一次修改的边界

将用户的一次连贯需求视为一次修改，例如“增加登录并删除旧游客模式”。不要每编辑一个文件就提交；一次修改只做一个完整、可验证的逻辑变更。

如果修改没有产生有效代码或配置变化，不创建空提交或重复版本。如果一次请求包含多个可独立发布的特性，先说明拆分建议，再按用户确认的范围执行。

## 工作流程

```text
结构化理解用户需求并明确验收标准
  → 调研类似应用并确定架构
  → 准备匹配的开发环境
  → 实现修改
  → 删除废弃功能与死代码
  → 补齐模块注释
  → 运行验证（已有应用修改跳过）
  → UI 应用自动截图并同步 README（渲染验证按变更类型执行）
  → 递增版本并生成带版本号的产物
  → 已有应用修改直接发布 / 新应用请求确认 / 文档与 Skill 自动发布
  → 提交、推送并发布 GitHub Release
```

### 1. 明确需求与验收标准

开始前识别：

- 要新增、修改和删除的行为。
- 目标平台、用户和主要使用场景。
- 可观察的验收条件。
- 是否存在数据迁移、公开 API 或界面兼容性要求。

需求不明确时，先提出最少的关键问题。不得通过保留旧实现来猜测需求。

### 2. 先调研架构，再准备环境

#### 新应用

不要以“本机已经安装什么”作为架构选型起点。按以下顺序执行：

1. 在网上搜索至少 2 个类似应用或产品，了解其功能形态、平台和交互方式。
2. 查阅候选架构与开发环境的官方文档，优先使用官方来源。
3. 从需求复杂度、目标平台、部署方式、性能、团队维护成本和生态成熟度比较候选方案。
4. 选择能够满足需求的最简单方案，不为了“先进”引入不必要的服务、框架或抽象。
5. 用一句话记录选型结论，并在回复中列出关键调研来源。
6. 再检测本机环境，仅安装缺失的工具；已安装的工具直接复用，不重复安装或擅自升级。优先使用项目级环境、锁文件和可复现安装命令。

选型结论使用以下格式：

```text
架构：<前端/后端/数据/部署方案>
理由：<最关键的两三个原因>
开发环境：<语言及版本、框架、包管理器、构建与测试工具>
被排除的方案：<方案及不采用的主要原因>
```

#### 现有应用

先读取项目清单、配置和关键入口，确认现有架构。调研用于解决当前需求，不借一次普通改版替换整个技术栈。

仅在用户明确要求迁移，或现有架构确实无法满足需求且用户批准迁移时，才更换架构。不得每完成一次修改就下载一套新环境。

#### 环境要求

- 使用官方安装方式，不运行来源不明的脚本。
- 固定运行时和主要依赖版本，优先提交项目已有的锁文件。
- 不覆盖系统级工具或用户全局配置，除非用户明确要求。
- 新应用安装环境后运行项目规定的安装、构建和测试命令，确认环境可用；已有应用修改按发布路径跳过这些验证。
- 环境问题与代码问题分开报告，不得把未验证的环境当作已就绪。

### 3. 实现最小完整修改

- 只实现已确认的需求，不顺手重构或增加假设性功能。
- 复用项目既有模式；只有现有模式无法合理满足需求时才新增抽象。
- 保持代码可构建、可测试、可回滚。
- 在边界处验证用户输入、外部 API 响应和文件内容；信任内部代码与框架保证。
- 不引入命令注入、XSS、SQL 注入、硬编码密钥或敏感信息泄露。

#### 组件库优先

- 开发 UI 时先检查项目现有组件库，优先使用其中的组件、变体、主题令牌和组合方式，不自行重写基础组件。
- 现有组件库能够满足需求时，不额外引入第二套组件库；通过组合、配置和主题扩展实现界面。
- 仅在组件库无法满足明确需求时定制组件，并说明缺失能力、定制边界和复用方式。
- 项目没有组件库时，根据已选架构引入匹配的组件库，再使用其组件完成开发。

#### 体验优先于体积

- 不把压缩应用体积作为首要目标，优先保证交互流畅、反馈及时、视觉一致、稳定可靠和可访问。
- 为提升体验，可以使用更完整的组件、动效、高质量素材或必要依赖，不因担心包体变大而削减体验。
- 仅在体积明显影响加载或响应且不损害体验时优化体积；不得为减小体积引入卡顿、缺失反馈或稳定性问题。

#### 截图与 README 同步

- 有 UI 的应用开发完成后自动截图；每次界面修改或更新后，必须重新拍摄受影响的页面和流程，不能沿用旧图。
- 截图覆盖主界面和关键操作流程，等待页面稳定加载后使用固定视口拍摄，保存为清晰、有意义的 PNG 文件。
- 优先沿用项目现有截图目录；没有约定时使用 `docs/screenshots/`。截图必须纳入当前项目仓库，不能只保存在临时目录。
- 在项目根目录 `README.md` 中新增或更新“截图”章节，使用相对路径 Markdown 图片、替代文本和简短说明；没有 README 时创建最小 README。
- 用新截图替换旧图，删除不再被引用或已失效的截图，并检查本地及 GitHub README 渲染后的图片链接和内容；已有应用修改只更新截图和链接，跳过渲染验证。
- 截图使用测试或脱敏数据，不包含密钥、令牌、个人隐私、内部地址或未公开信息。新应用、文档和 Skill 无法完成截图或 README 渲染验证时，标记为“未验证”，不进入发布流程；已有应用修改仍须更新截图和 README，但跳过渲染验证，并在发布说明中注明未验证。

### 4. 删除废弃功能，不保留死代码

每次修改完成后，盘点本次被替换或取消的功能：

1. 找出旧组件、页面、路由、接口、服务、状态、配置、静态资源和专用依赖。
2. 删除不再执行的代码、分支、函数、文件和旧测试。
3. 搜索旧名称、导入和引用，确认没有残留调用。
4. 删除或更新失效配置、环境变量和构建入口。
5. 更新仍有效的文档与注释，避免描述已删除行为。
6. 检查依赖是否还被其他模块使用；仅删除确认无引用的依赖。
7. 新应用运行构建与测试，确认删除没有破坏保留功能；已有应用修改跳过构建与测试。

禁止使用以下方式“保留”废弃实现：

- 注释掉旧代码。
- 添加永不开启的功能开关。
- 保留未使用的变量、导入、兼容层或占位文件。
- 复制旧逻辑到新模块旁但不调用。

用户明确要求保留的兼容接口除外。删除数据库字段或历史数据前必须单独确认；需要时保留最小迁移脚本，不留旧运行时代码。

### 5. 为每个模块添加职责注释

首次在项目中应用本 Skill 时，扫描全部业务源码模块；后续每次修改至少覆盖改动模块及其关联模块。

模块指承担独立职责的源码文件或内聚目录，例如组件、页面、服务、路由、数据访问层和工具模块。生成的代码、第三方依赖和锁文件不需要添加注释。

在模块入口添加一段简短注释，说明：

- 模块做什么。
- 职责边界或不负责什么。
- 关键输入、输出或外部依赖，仅在这些信息不易从代码看出时补充。

示例：

```ts
// 用户认证模块：负责登录、令牌刷新与权限校验；不保存用户业务资料。
```

要求：

- 使用项目语言习惯的注释语法。
- 每个模块至少一条模块级注释。
- 注释描述职责与约束，不逐句复述代码。
- 修改行为时同步更新注释；删除模块时删除注释。
- 不为显然易懂的表达式添加无价值注释。

### 6. 验证修改

已有应用的代码修改不执行本节任何验证，直接进入版本与发布流程，不因未验证阻止发布；生成发布产物所必需的构建除外，但不得将该构建表述为验证通过。仍须在发布说明中明确标注未验证。新应用、纯文档和 Skill 按项目已有命令执行适用的检查：

1. 格式化或静态检查。
2. 类型检查。
3. 单元测试、集成测试及相关回归测试。
4. 生产构建；已有应用修改仅在构建是生成发布产物的必要条件时执行，不进行构建结果验证。
5. 对 UI 或前端功能启动应用，在浏览器中验证主要流程和边界情况，并检查控制台错误。
6. 对 UI 应用自动截图，确认截图文件已纳入仓库、README 相对链接有效且 GitHub 渲染结果与最新界面一致；改版后确认旧图已替换。
7. 对打包产物检查文件内容、版本号和启动行为。

报告实际执行的命令及结果。不得声称未运行的检查已经通过。

若新应用、文档或 Skill 验证失败，修复后重新运行；无法完成验证时，保留本地修改并明确标记为“未验证”，不进入发布流程。已有应用修改不受此限制，但不得把跳过的验证表述为通过。

### 7. 递增版本并生成带版本号的产物

优先遵循项目已有的版本方案；没有方案时使用语义化版本：

- `PATCH`：修复缺陷，不改变公开行为。
- `MINOR`：新增向后兼容的功能。
- `MAJOR`：破坏兼容性的功能删除、架构或 API 变更。
- 新项目默认从 `0.1.0` 开始；用户已有要求时从其要求。

版本号规则：

- 每个发布的修改递增一次版本；补丁修复发布补丁版本，不重复使用旧版本。
- 使用单一版本来源，例如 `package.json`、`pyproject.toml`、`Cargo.toml` 或项目构建配置，再由构建流程注入产物。
- Git 标签使用 `v<版本号>`，例如 `v1.2.3`。
- 桌面程序、CLI 和压缩包的文件名包含版本号，例如 `my-app-1.2.3-windows-x64.zip`。
- 可执行程序在 `--version`、启动信息或“关于”界面中显示相同版本。
- 网站将版本写入构建元数据，并在页脚、健康检查或管理界面中可查询；若有发布压缩包，同样带版本号。
- 不手工修改构建生成的版本文件；改版本来源后重新构建。

新应用、文档和 Skill 在构建或打包后核对版本来源、标签候选版本、文件名和程序内显示版本一致；产物缺失、版本缺失或不一致时不发布。已有应用修改仍需生成带版本号的产物并递增版本，但不运行产物内容和启动验证，发布说明注明未验证。

### 8. 提交并发布

按变更类型选择发布路径：

- 已有应用的代码修改：跳过验证和发布确认，版本递增并生成带版本号的产物后，直接提交、推送、打标签并创建 GitHub Release；Release 说明注明“未验证：按用户要求跳过验证”。
- 新应用的代码修改：验证通过且产物带正确版本后，请求一次明确确认，收到同意后才提交和发布。
- 文档和 Skill：验证通过且发布条件满足后，直接提交并发布，不询问。
- 同时包含文档与应用代码的变更按应用代码处理；已有应用修改直接发布，新应用请求确认。

新应用代码使用以下确认提示：

```text
修改已完成并通过 <验证项>，版本为 vX.Y.Z。
是否现在提交到 Git、推送当前分支到 GitHub，并创建包含发布产物的 GitHub Release vX.Y.Z？
```

新应用代码未收到明确同意时，只保留本地修改，不提交、不推送、不创建 Release。已有应用修改无需等待确认，但仓库、远端、认证、权限和内容安全等发布前置条件仍须满足；条件不满足时停止并报告阻塞点。

#### 文档与 Skill 自动发布

文档或 Skill 同时满足以下条件时，直接提交、推送、打标签并创建 Release，不请求确认：

1. 内容、格式和适用验证已通过。
2. 当前目录已是 Git 仓库，且已有 GitHub 远端。
3. GitHub CLI 与登录状态可用，具备推送和发布权限。
4. 已确认没有密钥、凭据、临时文件和无关的用户改动。
5. 版本号已确定；需要分发打包时，产物已带版本号并验证。

若文档或 Skill 的验证、远端、权限或认证不满足，停止自动发布并报告阻塞点；已有应用修改仅检查发布前置条件，不执行代码验证。任何发布均不自行初始化仓库、创建 GitHub 仓库、强制推送或覆盖标签。

#### GitHub CLI 检测与安装

需要 GitHub CLI 时，按以下顺序处理：

1. 先检测当前 shell 的 `PATH` 和常见安装目录，确认 `gh` 是否已经存在。
2. 已存在时运行 `gh --version` 并直接复用，不重复安装、不擅自升级。
3. 仅在确认不存在时，使用用户批准的包管理器安装；安装会改变系统状态时先取得同意。
4. 安装后重新检测可执行文件，再运行 `gh --version` 和 `gh auth status`，确认工具可用且登录状态明确。
5. 若安装后仍找不到 `gh`，先诊断安装路径与 `PATH`，不得再次执行安装。
6. 已安装但未登录时，引导用户执行 `gh auth login`；不输出、提交或记录访问令牌。

执行发布时：

1. 检查 `git status`、完整 diff 和近期提交风格。
2. 确认没有密钥、凭据、临时文件或与本次修改无关的用户改动。
3. 仅暂存本次修改涉及的具体文件。
4. 创建一个提交，信息说明变更目的，例如 `feat: add account recovery flow`。
5. 推送当前分支到其 GitHub 远端；不强制推送。
6. 创建并推送 annotated tag `vX.Y.Z`；标签已存在时停止并请求处理，不覆盖旧标签。
7. 使用 `gh` 创建 GitHub Release，关联同一标签，上传带版本号的产物。
8. Release 说明包含本次新增、修改、删除内容和验证结果。
9. 检查远端提交、标签和 Release，确认发布成功。

前置条件与异常处理：

- 当前目录不是 Git 仓库时，不自行初始化或创建 GitHub 仓库，先说明缺少的条件。
- 没有 GitHub 远端或没有发布权限时，停在本地阶段并报告；`gh` 缺失时按上述检测与安装流程处理。
